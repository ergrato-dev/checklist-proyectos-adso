# Lista de Chequeo — Trimestre II

## Seguimiento de Proyecto Formativo · Cadena de Formación
### Programa ADSO Cód. 228118 | SENA — Centro de Gestión de Mercados, Logística y TI | Regional Distrito Capital

---

> **Modalidad:** Cadena de Formación (aprendices graduados como Técnicos en Desarrollo de Software)  
> **Equivalencia en el semáforo interno:** Trimestre III–IV del plan de formación  
> **Fase del proyecto formativo:** Arquitectura de Software + Propuesta Técnica — Proyecto II  
> **Competencias activas:** Análisis de la Especificación de Requisitos del Software · Elaboración de la Propuesta Técnica del Software · Modelado de los Artefactos del Software (inicio) · Construcción de BD — resultado parcial · HTML/CSS/Responsive  
> **Propósito del trimestre:** El equipo, que trae base técnica de la etapa de Técnico, profundiza en arquitectura de software, consolida el análisis mediante modelado UML avanzado, construye una propuesta técnica completa con estimación ágil (Scrum/backlog/costos) y avanza en el diseño de la interfaz web responsive. El nivel de exigencia es superior al T2 de Oferta Abierta en densidad técnica y en madurez de los artefactos.

## DIMENSIÓN 1 — Gestión del Proyecto (20 %)

> A diferencia del T1, en este trimestre el proceso de gestión debe mostrar madurez metodológica. Se espera que el equipo no solo use una herramienta de seguimiento, sino que la use con criterio ágil: sprints definidos, backlog priorizado, velocidad estimada y reuniones de revisión documentadas.

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 1.1 | 👁 El equipo tiene un **product backlog** documentado en la herramienta de gestión elegida, con historias de usuario priorizadas usando un criterio explícito (MoSCoW, valor vs. esfuerzo u otro). | | | | | |
| 1.2 | 🎤 El backlog está dividido en **sprints** con objetivo claro por sprint. El equipo explica cuántos sprints ha completado, qué se logró en cada uno y qué quedó pendiente. | | | | | |
| 1.3 | 👁 Existen **actas de las ceremonias Scrum** (o equivalente): al menos una acta de sprint planning, evidencia de daily y una de sprint review/retrospectiva del período. | | | | | |
| 1.4 | 🎤 Los **roles del equipo** (Product Owner, Scrum Master) son claros y operativos: el PO puede hablar sobre prioridades del negocio y el SM describe los impedimentos que gestionó; el equipo puede mostrar un **gráfico de burndown** que representa el avance real del sprint más reciente. | | | | | |

## DIMENSIÓN 2 — Artefactos Técnicos (40 %)

> Esta dimensión se divide en cuatro bloques que corresponden a las competencias activas del trimestre. Dado que los aprendices de Cadena ya traen base técnica, los artefactos deben mostrar mayor rigor que en Oferta Abierta.

### Bloque 2A — Arquitectura de software y modelado de análisis (RA 01 y 02 de Análisis)

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 2A.1 | 🎤 El equipo ha definido y documentado la **arquitectura candidata del sistema** (patrón elegido, justificación con RNF) y puede explicar **al menos dos principios SOLID** aplicados en una decisión de diseño o código del proyecto. | | | | | |
| 2A.2 | 👁 Existe un **diagrama de componentes** (UML o equivalente) que muestra los módulos principales del sistema, sus interfaces y cómo se comunican entre sí, coherente con la arquitectura declarada. | | | | | |
| 2A.3 | 👁 Existen **diagramas de casos de uso** en UML completamente trazables al SRS, y para los casos de uso críticos (mínimo 5) existen **plantillas extendidas** con flujo básico, flujos alternativos, precondiciones, postcondiciones y condiciones de excepción. | | | | | |
| 2A.4 | 👁 Existe un **modelo de dominio** actualizado con las clases conceptuales, sus atributos relevantes y las relaciones del negocio, distinguiéndose del diagrama de clases de diseño. | | | | | |
| 2A.5 | 👁 Existe al menos un **diagrama de actividades UML** por cada proceso de negocio principal, con calles de responsabilidad (swimlanes) cuando intervienen múltiples actores. | | | | | |

### Bloque 2B — Propuesta técnica del software (RA 01, 02 y 03 de Propuesta Técnica)

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 2B.1 | 👁 Existe una **propuesta técnica formal**: alcance, stack tecnológico con justificación, estimación de esfuerzo por sprints y cronograma de desarrollo. | | | | | |
| 2B.2 | 👁 La propuesta incluye **fichas técnicas** de los componentes tecnológicos principales (servidor, motor de BD, framework backend, framework frontend) con características, versión y tipo de licencia. | | | | | |
| 2B.3 | 👁 El equipo ha realizado una **estimación de costos** del proyecto: licencias de software si aplica, infraestructura estimada (hosting, nube) y costo del talento humano en horas de trabajo. | | | | | |
| 2B.4 | 🎤 Existe un **análisis comparativo de al menos dos alternativas tecnológicas** para un componente crítico con decisión argumentada, y el equipo puede indicar el tipo de **licencia** de los componentes de terceros usados y si es compatible con el uso que le darán. | | | | | |

### Bloque 2C — Modelo de datos relacional (RA 02 de Construcción de BD — resultado parcial)

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 2C.1 | 🎤 El **modelo lógico relacional** está completo y normalizado hasta 3FN (el equipo explica al menos un caso concreto de descomposición) y existe un **script SQL** (DDL) que crea la estructura sin errores en el motor seleccionado. | | | | | |
| 2C.2 | 👁 Existe un **diccionario de datos** completo: nombre de columna, tipo de dato con precisión, restricciones (PK, FK, NOT NULL, UNIQUE, CHECK) y descripción breve. | | | | | |
| 2C.3 | 👁 El equipo ha definido **políticas de seguridad de datos** básicas: qué campos deben cifrarse o enmascararse, qué niveles de acceso tendrán los roles del sistema y cómo se garantiza la integridad referencial. | | | | | |

### Bloque 2D — Diseño de interfaz y HTML/CSS/Responsive

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 2D.1 | 👁 Existe un **sistema de diseño básico** (paleta con mínimo 3 tonos, tipografías, criterios de espaciado) y un **mapa de navegación** (sitemap) que indica cómo se conectan todas las vistas y cuáles requieren autenticación. | | | | | |
| 2D.2 | 👁 Existe un **prototipo web en HTML semántico** para las pantallas principales (mínimo 5), con etiquetas estructurales correctas. | | | | | |
| 2D.3 | 👁 El prototipo usa un **framework CSS o CSS puro con metodología** (Tailwind, Bootstrap, BEM) de manera consistente, sin mezcla caótica de enfoques. | | | | | |
| 2D.4 | 🎤 El prototipo es completamente **responsive** en tres puntos de quiebre (móvil, tablet, escritorio), demostrable en las DevTools durante la sustentación. | | | | | |

## DIMENSIÓN 3 — Documentación (20 %)

> En Cadena de Formación la exigencia documental es mayor porque los aprendices ya tienen experiencia previa. Se espera documentación que un desarrollador externo pueda leer y entender sin necesidad de preguntarle al equipo.

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 3.1 | 👁 El **repositorio** tiene un `README.md` completo: proyecto, arquitectura elegida, stack tecnológico, pasos de instalación del entorno de desarrollo y cómo ejecutar el proyecto localmente. | | | | | |
| 3.2 | 👁 El **informe de análisis** tiene portada, control de versiones, tabla de contenido, y está redactado según NTC 1486 o APA. Incluye descripción del sistema, diagramas UML referenciados, modelo de datos y decisiones arquitectónicas. | | | | | |
| 3.3 | 👁 La **propuesta técnica** es un documento independiente bien estructurado (portada, resumen ejecutivo, alcance, stack, fichas técnicas, estimación de costos y cronograma por sprints), no integrado al informe de análisis. | | | | | |
| 3.4 | 👁 Todos los **diagramas** (UML, modelo de datos, arquitectura) están en el repositorio en formato editable y en imagen/PDF, y la **estrategia de ramas en Git** está documentada (`main`, `develop`, ramas por funcionalidad, PRs con descripción). | | | | | |

> Se observa en simultáneo con las demos de D2, sin tiempo adicional en la sesión.

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|

| 4.2 | 🎤 Todos los integrantes presentes **participan en la sustentación** con conocimiento real del artefacto que exponen. No hay "testigos mudos". | | | | | |
| 4.3 | 🎤 El equipo describe **cómo resolvió un conflicto técnico o de equipo** durante el trimestre (desacuerdo de diseño, integrante con bajo rendimiento, dificultad de coordinación) y qué estrategia aplicó. | | | | | |
| 4.4 | 👁 La **distribución de tareas** en el tablero de gestión es equitativa. No debería encontrarse que un solo integrante tiene el 90 % de las tareas asignadas y cerradas. | | | | | |

## DIMENSIÓN 5 — Calidad y Mejores Prácticas (10 %)

> Los aprendices de Cadena deben demostrar criterio técnico más allá de lo básico. No basta con que el código funcione: debe estar bien construido, documentado y tener trazabilidad de calidad.

| # | Criterio de evaluación | ✅ | 🟡 | 🔴 | ➖ | Observaciones del jurado |
|---|------------------------|----|----|----|----|----|
| 5.1 | 👁 El equipo tiene definido y documentado su **estándar de codificación**: convenciones de nombrado, reglas de indentación, política de comentarios. | | | | | |
| 5.2 | 👁 Los **prototipos** cumplen accesibilidad básica (WCAG nivel A) y el equipo realizó al menos una **revisión técnica entre pares** de algún artefacto con evidencia del proceso (comentarios en GitHub, acta o lista de chequeo interna). | | | | | |
| 5.3 | 🎤 El equipo identifica **al menos tres decisiones de diseño** (arquitectura, modelo de datos o interfaz) tomadas conscientemente pensando en mantenibilidad, escalabilidad o seguridad. | | | | | |
| 5.4 | 🎤 Los **modelos UML y el modelo de datos** son coherentes entre sí: si el jurado toma una entidad del modelo de dominio, debería encontrar su correspondencia en el modelo relacional. Si hay diferencias, el equipo las explica técnicamente. | | | | | |
