# Lista de Chequeo — Trimestre IV

## Seguimiento de Proyecto Formativo · Oferta Abierta

### Programa ADSO Cód. 228118 | SENA — Centro de Gestión de Mercados, Logística y TI | Regional Distrito Capital

---

> **Fase del proyecto formativo:** Construcción del Software — Proyecto IV
>
> **Resultados de Aprendizaje activos este trimestre:**
>
> - Construcción del Software → RA 03: Crear componentes front-end de acuerdo con el diseño — **resultado completo**
> - Construcción del Software → RA 04: Codificar el software de acuerdo con el diseño — **resultado parcial**
> - Construcción del Software → RA 02: Construir la base de datos — **resultado parcial**
> - Propuesta Técnica → RA 01: Definir especificaciones técnicas del software
> - Propuesta Técnica → RA 02: Elaborar propuesta técnica
> - Propuesta Técnica → RA 03: Validar condiciones de la propuesta técnica
>
> **Módulos técnicos activos:** Front End 1 React/TypeScript · REST Backend (Express, FastAPI o Spring Boot) — resultado parcial · SQL Extendido — funciones, procedimientos almacenados y triggers · Realización y Estimación de Propuesta Técnica
>
> **Propósito del trimestre:** T4 es el trimestre de construcción activa con el stack completo del programa. Por primera vez el equipo tiene un frontend SPA real (React/TypeScript) comunicándose con un backend REST funcional (usando Express, FastAPI o Spring Boot), respaldado por una base de datos con lógica programada (procedimientos y triggers). Simultáneamente, el equipo debe formalizar la Propuesta Técnica del proyecto, que es el documento que cierra el ciclo análisis → diseño → construcción y le da viabilidad contractual al sistema. El jurado en T4 evalúa **software funcionando de manera integrada**, no módulos aislados: el frontend debe hablar con el backend, el backend debe usar la base de datos, y la propuesta técnica debe describir ese mismo sistema que se está construyendo.

## DIMENSIÓN 2 — Artefactos Técnicos (45 %)

### Bloque 2A — Frontend SPA con React/TypeScript (RA 03 — resultado FINAL)

> Este RA se cierra definitivamente en T4. El jurado no puede aceptar un frontend en construcción preliminar: debe estar funcional, tipado, conectado al backend y demostrable en vivo. La exigencia es proporcional al hecho de que es el cierre del resultado.

| #    | Criterio de evaluación                                                                                                                                                                                                                                                                      | ✅  | 🟡  | 🔴  | ➖  | Observaciones del jurado |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- | --- | --- | ------------------------ |
| 2A.1 | 👁 La aplicación React/TypeScript **compila sin errores ni warnings de TypeScript**. El jurado puede solicitar `tsc --noEmit` o revisar la consola del navegador durante la demo.                              |     |     |     |     |                          |
| 2A.2 | 🎤 El frontend implementa **al menos cinco vistas funcionales** que corresponden a los casos de uso del proyecto: muestran datos reales de la API, permiten interacción y responden con feedback visual. El jurado pide una demo en vivo.        |     |     |     |     |                          |
| 2A.3 | 👁 El código TypeScript usa **interfaces o tipos definidos** para todos los modelos de datos del dominio (no `any` sin justificación), y el estado de la aplicación está gestionado de manera **organizada y predecible** (Context API, Zustand, Redux u otro); el equipo explica qué estado es global y por qué. |     |     |     |     |                          |
| 2A.4 | 🎤 El frontend implementa **autenticación y autorización** funcionales: login que obtiene un token, almacenamiento seguro, y rutas protegidas que redirigen al usuario no autenticado. Demo en vivo del flujo.                |     |     |     |     |                          |
| 2A.5 | 👁 La interfaz es **responsive** en móvil, tablet y escritorio con estilos coherentes (Tailwind, CSS Modules, styled-components u otro), y **maneja errores de red y de usuario** con mensajes útiles y validación en línea de formularios. |     |     |     |     |                          |

### Bloque 2B — Backend REST: segundo servicio funcional (Express, FastAPI o Spring Boot)

> El equipo elige la tecnología backend que mejor se alinee con su arquitectura. Este bloque evalúa que el equipo construye un servicio REST integrado con la BD, independientemente de la tecnología seleccionada.

| #    | Criterio de evaluación                                                                                                                                                                                                                                                                                                                         | ✅  | 🟡  | 🔴  | ➖  | Observaciones del jurado |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- | --- | --- | ------------------------ |
| 2B.1 | 👁 El servidor **arranca sin errores** y la API está documentada mostrando todos los endpoints (Swagger/OpenAPI, javadoc o README), organizados por recurso o router.                             |     |     |     |     |                          |
| 2B.2 | 👁 El proyecto implementa al menos **dos recursos REST completos** (CRUD) con validación de entrada y serialización de salida bien definidas, tipos correctos y mensajes de error descriptivos.                                                  |     |     |     |     |                          |
| 2B.3 | 👁 El proyecto sigue una **estructura de carpetas clara por capas o por dominio**: rutas/controladores, esquemas/validación, modelos de BD (ORM), servicios o repositorios. El archivo principal no contiene lógica de negocio.                                                         |     |     |     |     |                          |
| 2B.4 | 👁 La API implementa **autenticación JWT funcionando**: los endpoints protegidos verifican el token antes de ejecutar la lógica, compatible con el sistema de autenticación del proyecto (revisable en el código o con una petición de Postman).                                                                                             |     |     |     |     |                          |
| 2B.5 | 👁 El proyecto usa **variables de entorno** para configuración sensible (con `.env.example`) y tiene un archivo de dependencias actualizado; el equipo puede demostrar que **se instala y ejecuta en un entorno limpio** siguiendo el README.                                                                                  |     |     |     |     |                          |

### Bloque 2C — Base de Datos: SQL extendido (RA 02 — resultado parcial)

> En T4 la base de datos deja de ser solo esquemas y consultas para convertirse en una capa con lógica programada. Funciones, procedimientos almacenados y triggers son mecanismos que permiten encapsular reglas de negocio críticas directamente en el motor, garantizando su ejecución independientemente de qué aplicación acceda a la BD. El jurado debe verificar que el equipo entiende cuándo usar cada uno.

| #    | Criterio de evaluación                                                                                                                                                                                                                                                                      | ✅  | 🟡  | 🔴  | ➖  | Observaciones del jurado |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- | --- | --- | ------------------------ |
| 2C.1 | 🎤 El equipo tiene implementada al menos **una función SQL** específica del proyecto que encapsula un cálculo o transformación de datos del dominio, y explica por qué esa lógica vive en la base de datos y no en el backend.                         |     |     |     |     |                          |
| 2C.2 | 🎤 Existe al menos **un procedimiento almacenado** que ejecuta una operación de negocio compuesta (más de una instrucción DML, variables, control de flujo, manejo básico de excepciones) con propósito claro en el sistema. |     |     |     |     |                          |
| 2C.3 | 🎤 Existe al menos **un trigger** con un propósito funcional real (auditoría, validación de integridad no expresable como constraint, actualización de datos derivados), y el equipo explica qué evento lo dispara y qué acción ejecuta. |     |     |     |     |                          |
| 2C.4 | 🎤 Todos los objetos programables (función, procedimiento, trigger) están **versionados en el repositorio** como scripts `.sql` ejecutables desde una BD vacía, y el equipo domina **transacciones SQL**: puede explicar qué operaciones requieren `BEGIN/COMMIT/ROLLBACK` con un ejemplo concreto del proyecto.                      |     |     |     |     |                          |

### Bloque 2D — Integración frontend ↔ backend ↔ base de datos

> Este bloque no corresponde a un módulo aislado: evalúa la coherencia del sistema completo. Es el bloque más representativo del estado real del proyecto y el que el jurado debe verificar siempre con una demostración en vivo, no con capturas de pantalla.

| #    | Criterio de evaluación                                                                                                                                                                                                                                                                                                                    | ✅  | 🟡  | 🔴  | ➖  | Observaciones del jurado |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- | --- | --- | ------------------------ |
| 2D.1 | 🎤 El equipo realiza una **demo en vivo del flujo completo** de al menos un caso de uso: usuario interactúa con el frontend → llama a la API → consulta o modifica la base de datos → el resultado se refleja en la interfaz. Sin capturas de pantalla: código corriendo en el momento. |     |     |     |     |                          |
| 2D.2 | 🎤 El sistema maneja correctamente el **ciclo de autenticación completo**: login, token en header `Authorization: Bearer`, validación en endpoints protegidos, y logout que invalida la sesión.                                                                                           |     |     |     |     |                          |
| 2D.3 | 👁 No hay **datos hardcodeados** en el frontend: todos los listados, tablas y formularios consumen datos reales de la API. Si hay datos de ejemplo, están en la base de datos, no en constantes del código.                                                                      |     |     |     |     |                          |

## DIMENSIÓN 3 — Documentación y Propuesta Técnica (20 %)

> La Propuesta Técnica es el resultado de aprendizaje estrella de esta dimensión en T4. Es el primer documento del programa con carácter "contractual": representa el acuerdo entre el equipo de desarrollo y el cliente sobre qué se va a construir, con qué tecnología, en cuánto tiempo y a qué costo estimado. El jurado debe evaluarla con la misma rigurosidad con que un comité técnico evaluaría una propuesta de proveedor de software.

| #   | Criterio de evaluación                                                                                                                                                                                                                                                                                                                                                                                                          | ✅  | 🟡  | 🔴  | ➖  | Observaciones del jurado |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- | --- | --- | ------------------------ |
| 3.1 | 👁 La **Propuesta Técnica** es un documento formal con al menos: resumen ejecutivo, descripción del problema, alcance (qué incluye y qué no), stack tecnológico con justificación técnica, y metodología de desarrollo. No es un resumen del SRS: está orientada a convencer a un cliente. |     |     |     |     |                          |
| 3.2 | 👁 La propuesta incluye una **estimación de costos** con desglose (horas por rol, costo por hora, subtotal y total), coherente con el alcance descrito.                                                                        |     |     |     |     |                          |
| 3.3 | 👁 La propuesta incluye un **cronograma** (Gantt o tabla de sprints) con fases, fechas estimadas, hitos y dependencias, consistente con el backlog del proyecto.                                                                                                                |     |     |     |     |                          |
| 3.4 | 👁 La propuesta incluye un **análisis de riesgos técnicos y de gestión**: al menos cinco riesgos con probabilidad, impacto y estrategia de mitigación concreta, específicos del proyecto.                                                                       |     |     |     |     |                          |
| 3.5 | 👁 El **README del repositorio** describe cómo levantar el sistema completo y las variables de entorno necesarias; la **colección de Postman o documentación Swagger** cubre todos los endpoints implementados hasta T4, con ejemplos de petición y respuesta.                                                                                |     |     |     |     |                          |
