# Hay dominios que no agregan valor real al aprendiz y/o generan riesgos

## Criterio pedagógico y profesional

Dominios no aceptables/cuestionables

¿Por qué las líneas rojas son una decisión pedagógica, no una restricción arbitraria?

_Inventarios:_ El dominio está saturado hasta el punto de que resolver el problema no aporta ningún diferencial de aprendizaje. Un aprendiz que construye un sistema de inventarios en 2026 está resolviendo un problema que tiene soluciones industriales gratuitas (Odoo Community, ERPNext, incluso Excel avanzado) y que cualquier empresa con dos dedos de frente no le va a pedir construir desde cero. El proyecto formativo debe preparar para resolver problemas reales que justifiquen contratar un desarrollador; un inventario no lo hace.

_Contabilidad:_ Además del argumento de saturación, la contabilidad tiene regulaciones técnicas estrictas (plan único de cuentas, normativas DIAN en Colombia, NIIF). Un sistema contable mal construido puede causar daño real. El aprendiz no tiene el contexto legal para construirlo correctamente, y construirlo "de juguete" no enseña nada útil.

_Facturación:_ La limitante es directamente legal. En Colombia, la facturación electrónica está regulada por la DIAN con esquemas XML específicos, certificados digitales y sistemas de validación previa. No es un dominio donde un proyecto formativo pueda operar sin riesgo de consecuencias reales para quien lo use.

_Datos sensibles (salud, datos personales, menores):_ No es una prohibición total, pero sí un análisis cuidadoso. Un sistema de gestión de historias clínicas, por ejemplo, implica Ley 1581 de Habeas Data(en realidad TODOS los proyectos deben contemplar este cumplimiento), potencial exposición de datos sensibles y responsabilidades legales. Si un grupo quiere trabajar en el dominio de la salud, el jurado debe evaluar si el alcance propuesto evita el manejo directo de datos personales sensibles reales.

_Hardware específico no disponible en el ambiente de formación:_ Los proyectos cuya viabilidad dependa de hardware especializado que el SENA no proporciona ni garantiza —sistemas POS con impresoras fiscales, lectores de huella dactilar, dispositivos de pago (datáfonos), escáneres de código de barras industriales, entre otros— no son aprobables en su forma original, dado que la dependencia de un componente físico no disponible convierte al proyecto en inviable por razones logísticas, no técnicas.

_Aprobación con condiciones_
Esta restricción no aplica a proyectos que integran hardware de propósito general cuando el equipo demuestra que puede asumir su costo y operación de manera autónoma: un prototipo con microcontroladores Arduino o sensores básicos es viable si el grupo presenta explícitamente en la sesión de aprobación el listado de componentes requeridos, su costo estimado y su declaración de que asumen la responsabilidad de adquisición y mantenimiento, sin que esto genere ninguna obligación para el SENA ni para el instructor. En estos casos el jurado aprueba condicionado a esa declaración, y deja constancia escrita en el acta de que el hardware es responsabilidad exclusiva del equipo de aprendices.

## Tecnologías habilitadas

### ¿Por qué definir un stack de referencia?

Acotar las tecnologías no es una restricción arbitraria: es una decisión pedagógica. Un stack de referencia permite que los artefactos sean comparables entre grupos, que el jurado disponga de criterios técnicos compartidos y que el aprendiz acumule profundidad en herramientas industrialmente relevantes en lugar de dispersarse en opciones sin sustento formativo.

### Stack de referencia

| Capa                            | Tecnología                           | Notas                                                          |
| ------------------------------- | ------------------------------------ | -------------------------------------------------------------- |
| **Backend — API REST**          | JavaScript · Node.js con **Express** | Preferencia para proyectos con lógica de aplicación ligera     |
| **Backend — API REST**          | Python con **FastAPI**               | Tipado estático recomendado; alto rendimiento                  |
| **Backend — API REST**          | Java con **Spring Boot**             | Patrón estándar en entornos empresariales                      |
| **Frontend**                    | **React**                            | SPA; puede combinarse con Vite o Next.js                       |
| **Base de datos relacional**    | **PostgreSQL**                       | Preferencia para datos estructurados complejos                 |
| **Base de datos relacional**    | **MySQL** / MariaDB                  | Alternativa aceptada                                           |
| **Base de datos no relacional** | **MongoDB**                          | Cuando la naturaleza del dominio justifique esquema flexible   |
| **Contenerización**             | **Docker** / Docker Compose          | Deseable; suma en la valoración de Calidad y Mejores Prácticas |

### Arquitectura mínima requerida

Todo proyecto debe implementar al menos el patrón **MVC (Modelo-Vista-Controlador)** o una arquitectura en capas equivalente en separación de responsabilidades:

- **Modelo:** lógica de negocio y acceso a datos.
- **Vista / Presentación:** interfaz de usuario (React u otro cliente aprobado).
- **Controlador:** manejo de rutas y orquestación entre la capa de presentación y la capa de datos.

> El uso de patrones más avanzados (Clean Architecture, Hexagonal, etc.) es bienvenido siempre que el equipo demuestre comprensión explícita de la separación de responsabilidades durante la sustentación.

### Tecnologías fuera del stack de referencia

El uso de tecnologías distintas a las listadas no está prohibido, pero requiere **aprobación explícita del jurado en la sesión de T1**. El equipo debe justificar:

1. Que la tecnología no genera dependencia de hardware no disponible en el ambiente de formación.
2. Que existe documentación y material de capacitación accesible.
3. Que el instructor puede evaluar los artefactos resultantes con criterios equivalentes a los del stack de referencia.
