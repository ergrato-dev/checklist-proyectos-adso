# Benchmark de frontend: React vs Vue vs Angular

> **Contexto:** proyectos formativos ADSO (SENA) con frontend SPA que consume una API REST en **FastAPI** o **Express.js**.
> **Estado actual del instrumento:** solo se contempla **React/TypeScript** (ver `5.lineas-rojas-ideas-de-proyecto.md` y las listas T4–T7).
> **Objetivo:** contrastar objetivamente si esa decisión se sostiene frente a Vue y Angular.

---

## 0. Advertencia metodológica (léela primero)

- **No se ejecutaron mediciones propias.** Los puntajes son una evaluación **cualitativa razonada** con escala 1–5, basada en conocimiento general del ecosistema. Las cifras de mercado, descargas o *bundle size* **deben verificarse** antes de citarse en un documento oficial (npm trends, State of JS, Stack Overflow Survey, portales de empleo locales).
- El criterio "alineación con el programa" es **parcialmente circular** (React ya fue elegido). Por eso se incluye un análisis de sensibilidad en la sección 4.
- Esto es una **recomendación de apoyo a decisión**, no un veredicto técnico universal: los tres frameworks son maduros y válidos.

## 1. Panorama rápido

| Aspecto | React | Vue | Angular |
|---|---|---|---|
| Naturaleza | Librería de UI | Framework progresivo | Framework completo ("baterías incluidas") |
| Mantenedor | Meta + comunidad (React Foundation) | Comunidad (Evan You) | Google |
| Lenguaje recomendado | TypeScript (JSX/TSX) | TypeScript (SFC `.vue`) | TypeScript (obligatorio de facto) |
| Modelo de reactividad | Re-render + hooks (Compiler opcional) | Reactividad granular (Proxies/refs) | Signals + Zone.js/zoneless |
| Router / Estado / HTTP | Se eligen (React Router, TanStack Query, Zustand…) | Oficiales (Vue Router, Pinia) + fetch/axios | Incluidos (Router, HttpClient, DI, Forms) |
| Meta-framework | Next.js, Remix/React Router | Nuxt | Angular SSR / Analog |
| Móvil | **React Native** | Ionic/Capacitor, NativeScript (menos común) | Ionic/Capacitor, NativeScript |
| Libertad de arquitectura | Alta (riesgo: inconsistencia) | Media | Baja (opinionated: consistencia) |

## 3. Evaluación por criterio (escala 1–5)

### A. Alineación con RAP y continuidad

- **React (5):** ya es el estándar del instrumento y **React Native** reutiliza conceptos (componentes, hooks, estado, ciclo de vida). Un aprendiz que domina React en T4 llega a T5 con ventaja real.
- **Vue (2):** implicaría reescribir listas y criterios; el móvil quedaría desconectado (Ionic/Capacitor es viable, pero es otro camino).
- **Angular (2):** igual que Vue; además su curva choca con el ritmo de T4.

### B. Curva de aprendizaje

- **React (3):** el núcleo es pequeño (componentes, props, estado, efectos), pero **hay que tomar muchas decisiones** (router, estado, fetch, formularios) y los `useEffect` mal usados son la fuente clásica de bugs.
- **Vue (4):** la más amable: plantillas cercanas a HTML, reactividad intuitiva, documentación excelente. Es la mejor opción pedagógica *pura*.
- **Angular (2):** exige TypeScript, decoradores, inyección de dependencias, RxJS/Signals, módulos/standalone. Potente, pero es mucho para un primer contacto.

### C. Empleabilidad

- **React (5):** mayor volumen de ofertas en LATAM y a nivel global, y en Colombia ofertas tanto de startups como de consultoras.
- **Vue (3):** demanda real pero menor; más frecuente en empresas medianas y proyectos específicos.
- **Angular (4):** fuerte en banca, seguros y grandes corporaciones (perfil "enterprise"), muy relevante en Colombia por el sector financiero.

> Verificar con datos locales (Computrabajo, LinkedIn, Magneto) antes de afirmar proporciones.

### D. Ecosistema y documentación

- **React (5):** el ecosistema más grande (UI kits, tablas, formularios, gráficas, auth). Mayor cantidad de tutoriales y respuestas en español.
- **Vue (4):** ecosistema sólido y curado; documentación oficial de las mejores.
- **Angular (4):** oficial y coherente (Angular Material, CDK), menos variedad de terceros pero más estable entre versiones.

### E. Integración con FastAPI / Express

Los tres consumen REST sin problema. Las diferencias están en el **tipado extremo a extremo**:

- **FastAPI** publica **OpenAPI** automáticamente → se puede **generar un cliente TypeScript** (`openapi-typescript`, `orval`, `openapi-generator`) que sirve para los tres frameworks.
- **Express** no genera OpenAPI por defecto; hay que documentar con Swagger/`zod-to-openapi`, o compartir tipos si el equipo usa TypeScript en ambos lados.

| Framework | Puntaje | Nota |
|---|---:|---|
| React | 4 | Excelente con TanStack Query + cliente generado; requiere elegir la capa de datos |
| Vue | 4 | Igual con TanStack Query (Vue Query) o Pinia Colada |
| Angular | 5 | `HttpClient`, interceptores (JWT) y DI vienen de fábrica; encaja muy bien con clientes generados |

### F. Rendimiento y tamaño

Los tres son suficientes para el alcance de un proyecto formativo.

- **React (3):** *bundle* base mayor que Vue; el rendimiento depende de disciplina (memoización, listas grandes).
- **Vue (4):** reactividad granular y *bundle* pequeño.
- **Angular (3):** *bundle* base más pesado, mejorado con Signals y *standalone components*.

### G. Tooling, DX y testing

- **React (4):** Vite + Vitest + Testing Library + Playwright; muy bien soportado, aunque hay que armar el stack.
- **Vue (4):** `create-vue` entrega un stack coherente (Vite, Vitest, Playwright, ESLint).
- **Angular (5):** CLI completo (generadores, testing, lint, build) sin decisiones extra.

### H. Estandarización evaluable

- **React (2):** dos equipos pueden tener arquitecturas totalmente distintas. La lista de chequeo debe compensarlo con **reglas explícitas** (ver sección 6).
- **Vue (4):** convenciones más claras (SFC, `<script setup>`, Pinia).
- **Angular (5):** estructura impuesta por el framework; el evaluador sabe dónde mirar.

## 5. Fortalezas y riesgos por opción

### React

| Fortalezas | Riesgos |
|---|---|
| Un solo modelo mental para web y móvil (React Native) | Demasiadas decisiones abiertas → arquitecturas dispares |
| Mayor demanda laboral y ecosistema | Mal uso de `useEffect` y estado derivado |
| Excelente soporte con TypeScript y Vite | Cambios de paradigma (Server Components, Compiler, frameworks) pueden confundir |
| Recursos de aprendizaje abundantes | Calidad muy variable de tutoriales antiguos (clases, Redux legacy) |

### Vue

| Fortalezas | Riesgos |
|---|---|
| Curva más suave; ideal para primer contacto | Sin puente natural hacia el móvil nativo del programa |
| Convenciones claras y documentación excelente | Menor oferta laboral relativa |
| Rendimiento y *bundle* pequeños | Comunidad más fragmentada entre Options API y Composition API |

### Angular

| Fortalezas | Riesgos |
|---|---|
| Estructura impuesta: fácil de evaluar y mantener | Curva empinada para aprendices en formación |
| Todo integrado (HTTP, forms, router, DI, testing) | Mayor carga conceptual (DI, RxJS/Signals) |
| Muy valorado en sectores corporativos | Sin continuidad hacia React Native |

## 6. Recomendación

### 6.1 Decisión

**Mantener React + TypeScript como estándar único del instrumento.**
El motivo principal no es que sea "mejor", sino que combina **continuidad con React Native (T5)**, **mayor empleabilidad** y **mayor ecosistema**, y permite mantener **una sola lista de chequeo** sin multiplicar criterios por framework.

### 6.2 Mitigar la debilidad principal de React (falta de estandarización)

Como Vue y Angular ganan en estructura, conviene **compensarlo en la lista de chequeo** con un stack de referencia obligatorio o recomendado:

| Capa | Estándar sugerido |
|---|---|
| Build | **Vite** + TypeScript en modo `strict` |
| Router | React Router |
| Datos del servidor | **TanStack Query** (evita `useEffect` + `fetch` manual) |
| Estado global (solo si hace falta) | Zustand o Context |
| Formularios y validación | React Hook Form + Zod |
| UI | Tailwind CSS o una librería de componentes (MUI, shadcn/ui) |
| Pruebas | Vitest + Testing Library; E2E con Playwright |
| Calidad | ESLint + Prettier |
| Gestor de paquetes | **pnpm** (o yarn) |

**Ítems de lista de chequeo que se pueden derivar** (sugerencia, no modificado en este documento):

- Estructura de carpetas por *feature* documentada en el README.
- Sin llamadas `fetch`/`axios` directas dentro de componentes: usar una capa `api/` o hooks de TanStack Query.
- Sin tipos `any` no justificados; TypeScript en `strict`.
- Variables de entorno (`VITE_API_URL`) fuera del código; sin secretos en el frontend.

### 6.3 ¿Y si un grupo quiere Vue o Angular?

Propuesta de política, para no cerrar la puerta sin romper la evaluación:

- **Por defecto:** React (todas las listas aplican tal cual).
- **Excepción justificada:** permitir Vue o Angular **solo** si el grupo (a) entrega justificación técnica escrita, (b) el instructor puede evaluarlo y (c) se acepta que el ítem de React Native se cumpla con la alternativa que se acuerde. Es un criterio de **flexibilidad controlada**, consistente con lo ya hecho para bases de datos.

## 7. Integración con la API: ejemplos listos para usar

### 7.1 Crear el proyecto (con pnpm)

```bash
pnpm create vite@latest frontend --template react-ts
cd frontend
pnpm install
pnpm add @tanstack/react-query react-router-dom zod react-hook-form
pnpm add -D openapi-typescript
```

### 7.2 Variables de entorno

```bash
# .env (no versionar; incluir .env.example en el repositorio)
VITE_API_URL=http://localhost:8000
```

### 7.3 Cliente HTTP tipado y centralizado

```ts
// src/api/client.ts
const API_URL = import.meta.env.VITE_API_URL as string;

export class ApiError extends Error {
  constructor(public status: number, message: string) {
    super(message);
  }
}

export async function api<T>(path: string, init: RequestInit = {}): Promise<T> {
  const token = localStorage.getItem("token"); // ver nota de seguridad abajo
  const res = await fetch(`${API_URL}${path}`, {
    ...init,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...init.headers,
    },
  });
  if (!res.ok) throw new ApiError(res.status, await res.text());
  return res.status === 204 ? (undefined as T) : ((await res.json()) as T);
}
```

> **Buena práctica de seguridad:** guardar el JWT en `localStorage` es sencillo para aprender, pero expone el token a XSS. Para producción, preferir **cookies `HttpOnly` + `SameSite`** emitidas por el backend.

### 7.4 Consumo con TanStack Query (en lugar de `useEffect` + `fetch`)

```tsx
// src/features/tasks/useTasks.ts
import { useQuery } from "@tanstack/react-query";
import { api } from "../../api/client";

export interface Task {
  id: number;
  title: string;
  done: boolean;
}

export const useTasks = () =>
  useQuery({ queryKey: ["tasks"], queryFn: () => api<Task[]>("/tasks") });
```

```tsx
// src/features/tasks/TaskList.tsx
import { useTasks } from "./useTasks";

export function TaskList() {
  const { data, isPending, error } = useTasks();

  if (isPending) return <p>Cargando…</p>;
  if (error) return <p role="alert">Error: {error.message}</p>;

  return (
    <ul>
      {data.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
```

```tsx
// src/main.tsx
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { createRoot } from "react-dom/client";
import { TaskList } from "./features/tasks/TaskList";

const queryClient = new QueryClient();

createRoot(document.getElementById("root")!).render(
  <QueryClientProvider client={queryClient}>
    <TaskList />
  </QueryClientProvider>,
);
```

### 7.5 CORS: el error más común al conectar frontend y API

**FastAPI**

```python
# main.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],  # origen de Vite; nunca "*" con credenciales
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**Express**

```js
// server.js
import express from "express";
import cors from "cors";

const app = express();
app.use(express.json());
app.use(
  cors({
    origin: process.env.CORS_ORIGIN ?? "http://localhost:5173",
    credentials: true,
  }),
);
```

### 7.6 Tipos generados desde FastAPI (tipado extremo a extremo)

FastAPI expone el esquema en `/openapi.json`. Con eso el frontend evita duplicar y desincronizar tipos:

```bash
pnpm exec openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts
```

Agregarlo como script en `package.json`:

```json
{
  "scripts": {
    "gen:api": "openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts"
  }
}
```

> Con **Express** esto requiere documentar la API con OpenAPI (Swagger); si el equipo no lo hace, los tipos se escriben a mano o se comparten en un paquete común. Es una ventaja concreta de FastAPI para el criterio E.

## 8. Cómo validar este benchmark con datos propios (siguiente paso sugerido)

Para pasar de "evaluación cualitativa" a "evidencia", se propone un experimento pequeño y reproducible:

1. Implementar la **misma app** (login JWT + CRUD de una entidad + 3 vistas) en los tres frameworks contra la misma API.
2. Medir: tiempo para completar por un aprendiz de T4, líneas de código, tamaño del *bundle* (`pnpm build`), Lighthouse, cantidad de errores comunes.
3. Encuestar a instructores sobre la facilidad de evaluar cada resultado con la lista de chequeo.
4. Contrastar con ofertas laborales reales de la región (conteo por palabra clave en portales de empleo).

Si quieres, puedo preparar el repositorio esqueleto de ese experimento (API mínima en FastAPI + plantillas de los tres frontends).

## 9. Resumen ejecutivo

| Pregunta | Respuesta |
|---|---|
| ¿Es válida la decisión de usar solo React? | **Sí**, pero por razones de **continuidad, empleo y ecosistema**, no por superioridad técnica. |
| ¿Cuál es el mejor para aprender? | **Vue** (curva más suave). |
| ¿Cuál es el más fácil de estandarizar y evaluar? | **Angular**. |
| ¿Cuál se conecta mejor a FastAPI/Express? | Los tres bien; con **FastAPI + OpenAPI** el tipado extremo a extremo es un plus para cualquiera. |
| ¿Qué riesgo hay que cubrir si se mantiene React? | Falta de estandarización → definir stack de referencia (sección 6.2). |
| ¿Se debe abrir a otros frameworks? | Solo como **excepción justificada**, no por defecto. |
